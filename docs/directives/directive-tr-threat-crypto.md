# TR-2: the threat model, and the crypto in the open

Read first: directive-r4-common.md, docs/transparency.md §1 items 2 and 5 (the brief; Paul's words), src/kit/crypt.ts (PBKDF2 → AES-GCM), src/kit/sign.ts (Ed25519 with the P-256 fallback), src/kit/envelope.ts (the signed message), src/kit/short.ts and tinier/ (AES-256-GCM short links, the key in the fragment, the owner capability, schema.sql, what is stored and for how long), src/kit/privacy.ts and privacy-dialog.ts (key storage under Saved), src/kit/link-guard.ts, pictures.ts and media/ (the proxy), docs/network.md, the existing crypto tests under test/.

Build, plain words, no reassurance, no marketing:
1. `docs/threat-model.md`: what is protected against (the host learning a document; the short-link service reading one; a shared link altered in transit; a scam link or a tracking picture inside a document; a reader fetching a picture and revealing their IP; a lost phone with Saved on), what is not (someone you gave the link to passing it on; a compromised device, browser or extension; a weak password; the browser's own history and sync holding the URL; a screenshot), and for each design choice the threat it answers. One section on what the Cloudflare host can see (requests for the static files, the shortener's ciphertext rows, the proxy's picture fetches) and what it cannot. A section "If you find a hole" pointing at SECURITY.md (TR-3 writes it; link the name).
2. `docs/crypto/password.md`: PBKDF2 parameters (hash, iterations, salt length), AES-GCM (key length, IV length, tag), the sealed payload's exact byte layout and its text form (`E…`), the version byte, what an attacker with the link can do (offline guessing: say the cost), and WebCrypto with no library. `docs/crypto/signing.md`: Ed25519 and when P-256 is used instead, the envelope's exact signed message (bytes, order, what the name and date are), key generation and storage (where under Saved, exportable or not), what a signature proves and does not. `docs/crypto/short-links.md`: AES-256-GCM, key in the fragment, what tinier stores (schema.sql: fields, sizes), expiry and extension, the owner capability, what its logs hold (nothing: say how that is enforced), the expiry banner.
3. Test vectors: `test/crypto-vectors.test.ts` with fixed inputs (a password, a salt, an IV, a message, a key pair as JWK) and the exact expected outputs for password sealing, signing and the short-link cipher, checked against crypt.ts, sign.ts and short.ts, and the vectors written as JSON in `test/vectors/*.json` so another implementation can check them. If crypt.ts draws its salt and IV inside, add an internal entry point that takes them (not exported from the kit's public surface, marked for tests) rather than weakening anything.
4. docs/transparency.md: mark items 2 and 5 built with the date and the file names; the About dialog gets a line linking the threat model.
