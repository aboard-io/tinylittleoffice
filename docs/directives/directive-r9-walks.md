# R9-walks: random walks over the editor's state machine

Read first: directive-r9-common.md, src/kit/commands.ts (R9-commands: the registry is where the walk's actions come from), src/kit/chrome.ts and shell.ts as round eight left them, src/kit/dialog.ts, drawer.ts, menu.ts, context.ts, complete.ts, link-pop.ts (everything that opens and takes focus), src/kit/route.ts and codec.ts (the link), test/browser/helpers.ts, test/browser/perf.test.ts (the budget), fast-check's model-based testing (`fc.commands`, `fc.modelRun`/`asyncModelRun`): a dev dependency, test only.

Why: the bugs found by hand on a phone this week (the bar parked mid-screen, a dialog cut by the edge, the keyboard taking focus) are invariants broken after some sequence of actions. A machine walks thousands of sequences.

Build:
1. **The model.** A small typed model of the chrome: `{ app, mode: 'editing' | 'presenting', open: null | 'drawer' | 'dialog' | 'menu' | 'context' | 'palette', focusWas: string | null, scrolled, size }`. Commands for the walk: every registry command in force for the state (through `when`), the keys Escape, Tab, Shift+Tab, Enter, the arrows, Mod+A, typing a word, a tap outside, a scroll of the column, opening the drawer, a menu, the Share dialog, the templates, the palette, a pinch step, the visual viewport shrinking and growing (a phone's keyboard), a route change to another app and back. Each has `check(model)` (is it allowed now) and `run(model, real)`: do it in the real DOM and advance the model.
2. **The invariants**, asserted after every step, each with a message naming the step sequence: the focused element is inside whatever is open, else inside the editor or the chrome; after Escape (or a close) the focus is where it was before the thing opened; at most one modal `<dialog>` is open; `window.scrollY` is 0 and the column scrolls instead; the link in the address parses back to the document the editor holds (`write(parse)` equal) once the projection flushes; the bar is one row and inside the viewport; no element with text overflows the viewport sideways; `document.documentElement.scrollWidth <= innerWidth`; nothing `aria-hidden` holds the focus; every open thing has an accessible name; the perf budget per step holds (the keystroke budget of perf.test.ts, measured on the typing steps).
3. **The runs.** One test per app family (text: Write, Outline, Deck; grid: Sheet, Cal; canvas: Draw, Diagram, Anim; lists: Board, Todo, Trip; Site), 200 steps each, seeded, at 390×844 with a coarse pointer and at 1440×900, with the seed printed so a failure replays (`fc` does this: keep the shrunk counterexample in the message). The whole set runs under two minutes on the box, or it is split and the long ones marked for `npm run walks` rather than the default `npx vitest run` (say which in the report; the default suite must stay under its current time).
4. What the walks find, the builder fixes where the fix is small and certain, and reports otherwise as numbered findings with the replaying seed, one per invariant broken, for the next round.

Tests: the walks themselves; a node test that the model's command set covers every registry command in force in at least one state (so a new command joins the walk by being registered).
