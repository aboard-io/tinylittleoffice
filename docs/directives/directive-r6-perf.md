# R6-perf: a keystroke costs what the keystroke changed, not the whole document

Read first: directive-r6-common.md, src/kit/element.ts (DocElement.edit → emit: read(), write(), `seen`, `value`, requestUpdate, docchange), src/kit/shell.ts (onDocChange → change → envelopeOn, setTitle, checkSignature, encodeDoc, writeLink → payloadLength, keepSoon, history.replaceState, setTitle again; every `parseHash(location.hash).payload` and `location.href` read, which treat the link as the document; the meter at ~810 that uses payloadLength), src/kit/codec.ts (packDoc: two deflates at level 9 per encode), src/apps/write/editor.ts (willUpdate's echo guard that calls write() and parse(); the bar's lookItems/alignItems/paperItems/inserts built on every render; onSelect → requestUpdate on every text-select; the foot's word count), src/kit/text.ts (updated(): text-select dispatched after every draw), src/kit/icons.ts (`icon()` and `attrs` at ~190: SVG attributes rebuilt for every icon on every render), src/kit/i18n.ts (`plural` at ~63-70), src/kit/history.ts.

Paul (2026-10-10): "I'm deep in the word processor at around 700 words and it's starting to feel really slow. Do we want to come up with a strategy where we're not compressing the entire doc with every keystroke? We probably need to. And if that applies to the Word Processor it probably applies everywhere." His document: https://pefdev.exe.xyz:4179/#/v1/write/<payload: the one line of this directive's sibling file r6-perf-payload.txt>; 467 words, 2,870 characters, 1,908 characters of link.

Measured (2026-10-10, Chromium on the dev box, that document, 50 characters typed at the end; the CPU profile's self time over the 50): fflate 137 ms, TLO parse (parseInline, splitAttrs, parse) ~100 ms, garbage collection 54 ms, setBaseAndExtent 27 ms, i18n `plural` 25 ms, history.replaceState 23 ms, icons' attrs 17 ms, Lit 30 ms, the Write bar's menu items 5 ms; about 18 ms of script per keystroke on a fast desktop, so 50 ms and more on a phone, plus layout. Under node: parse 0.8 ms, write 0.5 ms, encodeDoc 10.6 ms for this document (two level-9 deflates). The whole document is parsed several times per keystroke: the shell's `def.title(doc)` (twice: onDocChange while fresh, keepSoon), `firstWords`, the editor's echo guard, checkSignature's read. None of this is needed to show the letter.

The strategy (one mechanism, in the kit, so every app has it):
1. **The keystroke path does only the keystroke.** In DocElement.edit the ops are applied, the view read, the host drawn, the undo entry recorded, and `docchange` still fires synchronously with the text (the contract every host and the shell rely on; `write` is ~1 ms and stays). Everything the shell does *with* that text is a projection of the document into the link, and the projection is made when typing pauses: `change()` stores the document and schedules `project()` ~150 ms after the last change (one timer; a burst of typing makes one projection). `project()` is: envelopeOn if needed, encodeDoc (once), writeLink (replaceState, payloadLength, keepSoon — which keeps its own 800 ms), setTitle, checkSignature. It is flushed at once, synchronously, before anything reads the link as the document: pagehide, visibilitychange→hidden, the window's blur, Share and every copy of the link, Display, print and every export, the QR code, a short link, the Compare view, a route change within the app, the library's keep, and the password lock. One `flushLink()` on the shell, called from each of those (grep every `parseHash(location.hash).payload`, `location.href` and `encodeDoc(this.doc)` in shell.ts and the kit, and route each through it). Under a password the pack is already asynchronous; it joins the same schedule. The shell's own re-render on a change (the meter, the title, the Saved state) happens at projection time, not per keystroke: make sure `change()` itself does not trigger a Lit update of the whole shell (check which reactive properties it sets).
2. **The editor does not re-read its own text.** The shell echoes `.value` back; DocElement already keeps `seen` (the text it last emitted). The echo guard in the Write editor (and any other host that compares `value` to `write(this.doc)`) compares to `seen` by identity and does nothing when they are equal; only a value that is not ours (an undo from the shell, a title typed in the bar, a document loaded) is parsed. The retitle the shell does while `fresh` is a `head` op the editor can apply without a full parse: have the shell send the head op through the existing path rather than re-sending the text, or at least once, not per keystroke.
3. **The bar draws when what it shows changes.** `text-select` fires after every draw; the Write host (and Deck, Outline, Site) call requestUpdate on each. Compute what the bar depends on (the marks under the caret, the block kind, the alignment, the look, the paper, undo/redo depth, whether a card is in hand) as one small key and skip the update when the key is unchanged. The menu item arrays (lookItems, alignItems, paperItems, inserts) are built lazily when the menu opens, not on every render. In icons.ts, memoize `icon(node, size, cls)`'s template per node and size (a WeakMap keyed by the node): the attrs string of an icon is computed once, not on every bar draw.
4. **Small costs that add up.** i18n `plural`: cache the Intl.PluralRules per language (or whatever ~63-70 rebuilds per call). The foot's word count: counted from the ops' touched blocks or on the projection, not on every keystroke if it is more than trivial. GC pressure: look at what allocates per keystroke in the profile (textops' ops arrays, `inherit`'s sets, the runs copied) and trim what is cheap to trim; do not restructure.
5. **Compression itself.** On the projection, encodeDoc stays as it is (both deflates, level 9: the shortest link matters and 11 ms once per pause is fine). Do not move it to a Worker.
6. **The limit.** This document is at 1,908 of the 2,048 characters a link may hold. Check what the Word Processor does at the limit today (the meter, the "too long" state: can the person keep typing? is anything lost?) and say in the report; change nothing there without a word from Paul unless typing past the limit loses text, in which case it is a bug: fix it so the document is never lost (the editor keeps the text; only the link stops updating and says so).

Tests (browser, PW_PORT=4444, against a 1,500-word document built in the test): typing 40 characters quickly calls history.replaceState at most twice (spy on it) while `docchange` fires 40 times; the link holds the latest text 300 ms after the last key; blur, pagehide and the Copy-link path each flush synchronously (the link is current before the handler returns); a reload after typing shows the typed text; undo after a pause still works; the bar's render count over 40 keystrokes of plain typing is under 5 (count renders with a test hook or a MutationObserver on the bar); a budget test: the synchronous work of one keystroke (time from dispatching the beforeinput to its return, median of 40) is under 12 ms on the dev box for the 1,500-word document, with the measured number in the report. Also tried by hand and reported: the Spreadsheet with 300 rows, the Outliner with 300 nodes, the Presentation Builder with 40 slides — the same path, so the same gain; name any app whose own per-edit work (the sheet's recalculation) is now the biggest cost.
