# Cleanup, second pass: structure

Paul asked "What else can we clean up" and said "Deal with all of that." These are the structural items; behaviour and public API (packages/doc exports, URL formats, the TLO grammar) must not change. Ponytail minimalism: apps are definitions on one small kit.

Do in this order, WIP-committing after each:

1. **Per-app CSS out of styles.css** (4,680 lines, 133 sections; only anim, calc, invoice, outline, site, web have their own file). Move each remaining app's rules into `src/apps/<id>.css` imported by its editor module (sheet, write, deck, draw, cal, todo, board, gantt, trip, and the diagram family where there is an editor module; diagram apps with no editor keep their few rules in styles.css in one clearly headed section). styles.css keeps only the kit: tokens, themes, shell, the one bar, widgets, print, responsive and a11y blocks. Cascade safety is the whole risk: gate it with screenshots. Before moving anything, take a Playwright screenshot of every app's editor (desktop 1100 wide and iPhone 390, light and dark; a single targeted spec run with `--workers=1`, chromium is enough) into the scratchpad; after each app's move, re-shoot that app and compare pixel-for-pixel (Playwright's `toHaveScreenshot` or a small PNG diff with `pngjs` from devDependencies if present, else write the diff with the Canvas in a node script... simplest: `expect(await page.screenshot()).toMatchSnapshot()` against the before set). Any difference must be understood and either fixed (rule order) or justified in the report with the pixel count. Keep the responsive/a11y blocks at the end of styles.css applying after app files: Vite bundles imported CSS in import order, so app CSS imported by an editor module loads *after* styles.css if styles.css is imported first in main.ts — verify the built `dist/assets/style-*.css` order and the token overrides for dark mode still win where they must.
2. **Templates into their apps.** src/lib/templates.ts (465 lines) holds every app's templates. Move each app's list next to its definition (`src/apps/<id>.templates.ts` or a `templates` field on the AppDef, whichever the kit already supports best), keep `templates(app)` in packages/doc working with the same output, and keep the template picker and the tests unchanged in behaviour.
3. **The new-app scaffold** (scripts/new-app.mjs) must generate today's pattern: an AppDef plus an editor with the one bar (`.to-toolbar`), `<to-insert>` when it has things to insert, direct manipulation, no Add buttons, its own `src/apps/<id>.css`, a unit test and a DOM test stub, a README row reminder. Run it once in the worktree to prove it (then delete the generated app) and say so.
4. **Test helpers**: test/dom/helpers.ts, helpers-more.ts, helpers-shell.ts, helpers-apps.ts → one `test/dom/helpers.ts` (sections with headings), imports updated, nothing else changed.
5. **Private exports**: these are exported but used only in their own file — make them private (drop `export`), unless a test imports them: animmodel DEFAULT_FRAMES, chart sankeyPage, codec toBase/fromBase, crypt PBKDF, diagram asItems, embeds LOOKUP_HOST, icons iconInner, markdown unwrapMarkdown, privacy PREFS, short TINIER, sitemodel defaultTheme/isPicture, tlo COL_TYPES, browser ToEmbed. Re-check each with grep across src test e2e packages scripts before touching it (some may have gained users today).
6. **Share cards**: public/og lacks outline, links, calc, web (web is hidden: skip it). Chromium is installed for Playwright; run `npm run icons` (or the og part of scripts/make-icons.mjs) for just the missing three if the script allows, else for all, and commit the PNGs. If the generator cannot run headless here, say so.
7. **.env files**: `.env` and `.env.development` are tracked and hold only VITE_SITE_URL and VITE_TINIER. Move those two values into vite.config.ts `define` (per mode) and delete the files from git, keeping `.env.example` with the two names documented; make sure the dev server's tinier proxy and the build's site URL still work (check scripts/deploy.mjs and README for mentions).

Then the usual: `npm run typecheck`, `npm run test:unit`, targeted vitest, one full `npx vitest run`, one `npm run build`. Report lines moved per app, screenshot diffs (count of apps identical / explained), what changed in the scaffold, and anything left alone with the reason.
