# R6-text: Select All in a document, and the page that would not stay scrolled up

Read first: directive-r6-common.md, src/kit/text.ts in full (readSel/readPos/domPoint, onSelectionChange, flushSel and keepCaretVisible, emit's `how`, the `sel` setter that sets pendingSel='focus' (~line 223), updated(), the Mod+A branch in onKeyDown which only acts for a line or lines), src/kit/textops.ts (clampSel, skipEmbed, ordered), src/apps/write/editor.ts (onKey, onCardKey, every `this.text.sel =`, the history's restore, how `docchange` flows to the shell and back), src/kit/shell.ts (what it does on docchange: autosave, the title, any re-set of the editor's document), docs/editing.md §Mod+A ("Select all: the words of the box first; pressed again with the box whole, everything in the document").

Paul (2026-10-10): "Mod+A in the Word Processor does not select all. That seems symptomatic." And: "I can't scroll back up in the writer after I make a big doc. It just keeps pushing me back down."

Build:
1. **Select All in a `doc`.** Reproduce first in a browser test: a Word Processor document of headings, paragraphs, a list, a table card and a picture card; the caret in the middle; Mod+A; the editor's `sel` must span from the first position of the first words to the last position of the last words, the DOM selection must cover every block, and Backspace then removes everything (cards too). Suspects: the browser's own select-all in the editing host puts the anchor on `.tx` itself or inside a card (contenteditable=false), readPos returns null or skipEmbed clamps away, and onSelectionChange treats it as "away"; or a host keydown takes the key. The fix belongs in `<to-text>`: Mod+A in a `doc` is handled by the editor as a model selection (anchor at the start of the first block, focus at the end of the last, cards included), written to the DOM through flushSel — the browser's own is not relied on. Then Mod+C copies the whole, Backspace/Delete empty the document to one paragraph, typing replaces the lot, Escape collapses to the focus. Check the same in the Outliner and the Presentation Builder (lines: the first press the box, the second the host) still hold, and docs/editing.md's row stays true.
2. **The page stays where the reader put it.** Reproduce first: a document of 300 paragraphs; type at the end; scroll to the top (window.scrollTo(0,0)); wait two seconds with no key pressed (an autosave tick, a word count, a history write may fire); assert scrollY is still 0. Then: scroll up, press one arrow key, assert the page did not jump to the caret unless the caret was off-screen. Suspects: keepCaretVisible after a draw the user did not type (flushSel runs from updated() whenever pendingSel is set; find who sets it when nothing was typed: the `sel` setter path at ~223 sets 'focus', and `focus()` at ~378/705/849 without `preventScroll`), the host re-setting `sel` on docchange or history, the shell re-setting the document after autosave. The rule to build: the page scrolls to the caret only after an edit the person made here (a typed character, a key, a command from the bar, a paste) and never after a render, a programmatic selection restore, an autosave, or a selectionchange the browser raised; every `focus()` in text.ts passes `{ preventScroll: true }` unless it is the one answering a user's command. Write the rule into text.ts's header.
3. Both fixes are in `<to-text>` or the Write host; name any kit file touched beyond these in `kitFiles`.
