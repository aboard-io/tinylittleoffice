# Translations: UX text and help in the person's language, automatically

Paul's words: "global usage, translation strings for help an UX text based on language displaying automatically". "Make sure to update the skills for agents."

Design (ponytail: one mechanism, no framework):
1. **One function.** `t(key or English text, vars?)` in src/kit/i18n.ts, the source string in English is the key (so code stays readable: `t('Insert')`, `t('{n} slides', { n })`), with ICU-light plurals (`{n, plural, one {# slide} other {# slides}}` or a simpler `{n|slide|slides}` form of our own — pick one, document it). Dictionaries are plain JSON per language in src/i18n/<lang>.json, loaded lazily as a chunk by language (English needs no file). Language chosen automatically from `navigator.languages` (first match on the primary subtag; `pt-BR` → `pt`), overridable from the hamburger ("Language: Automatic / English / Español / …", stored in localStorage) and by a `?lang=` or `#lang` only if cheap. `document.documentElement.lang` and `dir` set (Arabic/Hebrew get `dir=rtl` and the layout must survive it: check the one bar's fade and the sheet's column headers mirror sensibly; logical CSS properties where they are physical). Dates, numbers and money already use Intl where they do; check the sheet's number formatting, the calendar's day names and the date nav follow the chosen language too.
2. **Extract every UX string**: button labels, tooltips, menu items, placeholders, bar tooltips, dialog text, toasts, the templates' names and descriptions, the icon library's section names, the hamburger, the home/launcher tiles (app names and one-line descriptions), the help/about text and the privacy text. Not translated: document content, templates' sample text (keep English sample documents, or translate only the few words of the blank templates), app ids, URL formats, format keywords in the TLO grammar (`theme:`, `paper:` …), formula function names. Make the extraction mechanical: write a one-off script (scripts/i18n-extract.ts) that finds `t('…')` calls and writes/updates the JSON files with missing keys, and a unit test that every key used in code exists in every language file and that no language file has unused keys.
3. **No translations shipped — one file under management, edited by hand.** Paul: "don't translate but instead put all strings under management in one file so that an LLM can easily translate into a variety of languages" and "I'll edit that file by hand." So the file is for a person first: `src/i18n/en.ts`, a plain TypeScript module exporting one object (`export default { ... } satisfies Strings`), NOT JSON — so it can carry real `//` comments, trailing commas, and sections. Layout: a short header comment saying what the file is and how to translate it; then sections with a comment heading per area (`// The shell: menu, home, sharing`, `// The one bar`, `// Sheet`, `// Write`, …) in the order a person meets them; one line per string, English text as key and value (`'Add a column': 'Add a column',`), a trailing `// where/why` comment only where the words alone are ambiguous (e.g. `'Fill': 'Fill', // sheet: fill a range from its first cell`). Strings with `{placeholders}` and plural forms are explained once in the header. A translation is a sibling `src/i18n/<lang>.ts` with the same shape (the type checks that every key is present and nothing extra), found automatically via `import.meta.glob('./i18n/*.ts', { eager: false })` and loaded lazily; the hamburger lists what exists, named with Intl.DisplayNames; `navigator.languages` chooses. Ship English only. `src/i18n/README.md` (short): how a person or an LLM makes `xx.ts` (copy en.ts, translate values only, keep keys, placeholders and plural syntax, keep it short, house voice), and `npm run i18n:check`.
   **The extraction script must respect hand edits**: `scripts/i18n-extract.ts` scans `t('…')` calls, then (a) appends missing keys to the END of en.ts under a `// New — sort me into a section` comment, never reordering or rewriting existing lines or comments, and (b) reports (does not delete) keys no longer used, and placeholder mismatches between en.ts and any sibling. `npm run i18n:check` runs it in report-only mode and fails the unit test `test/i18n.test.ts` if a used key is missing from en.ts, so the file can never drift from the code. Prove the mechanism end to end in tests with an in-memory dictionary for a fake language; do not add a translated file to the repo.

4. **Help and UX text**: the About/Help screens and the one-line app descriptions in the launcher are the "help"; translate them. The README and docs stay English.
5. **Agents**: the skill template (skill/tinyoffice/SKILL.tpl.md) gains a short section: the UI follows the reader's language; documents are whatever language the author writes; an agent can set `lang:` in a document header to make the viewer's chrome follow the document's language (implement that header: it overrides the automatic choice for that document only). `npm run skill`.
6. Tests: a DOM test that registers an in-memory test dictionary for `es` (a dozen keys is enough), mounts the shell with `navigator.language = 'es'`, and sees those labels and `lang="es"`; that `lang:` in a document header switches; that the override in the hamburger persists; unit tests for plurals and fallbacks (missing key → English, missing language → English).

Pacing rules apply (one test command at a time; WIP commits). Keep the diff mechanical where it can be: `t()` wrapping should not change behaviour; the English tests must keep passing unchanged (English is the key).

7. **Native web APIs first** (Paul: "Do whatever you can to use the native web APIs btw, use the browser wisely."): no i18n library. Use `Intl.PluralRules` for plural categories (so `t()`'s plural forms are chosen by the language's real rules, not by n === 1), `Intl.DateTimeFormat`/`Intl.NumberFormat`/`Intl.RelativeTimeFormat`/`Intl.ListFormat` for anything formatted, `Intl.DisplayNames` to label the languages in the hamburger in their own names, `Intl.Locale` for `pt-BR` → `pt` and for text direction (`getTextInfo()`/`textInfo.direction` where available, with a short RTL list fallback), `navigator.languages`, and `document.documentElement.lang`/`dir`. Prefer CSS logical properties and `:dir(rtl)` for mirroring.
